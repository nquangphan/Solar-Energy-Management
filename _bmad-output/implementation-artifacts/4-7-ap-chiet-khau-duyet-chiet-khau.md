# Story 4.7: Áp chiết khấu + duyệt chiết khấu (biên ước tính)

Status: done

## Story

As a người có quyền áp chiết khấu,
I want áp chiết khấu và gửi đi duyệt,
so that giảm giá cho khách theo đúng quy trình kiểm soát (FR-18).

## Acceptance Criteria

1. **Endpoint Áp chiết khấu (FR-18, AD-18):** **Given** Đơn ở `baogia` có ≥1 dòng, **When** `POST /orders/:id/ap-chiet-khau` body `{amount, note?}` bởi người có `discounts.apply`, **Then** trong MỘT interactive transaction: (a) cổng atomic `updateMany({where: {id, status: 'baogia'}, data: {status: 'choduyet'}})` + `count === 1` (thua → sentinel → đọc lại → 409); (b) tạo `DiscountApproval` (`orderId`, `orderVersionId` = version hiện hành, `amount` integer đồng, `status: 'cho_duyet'`, `requestNote`, `requestedByAccountId` = actor). Publish `DiscountRequested` SAU commit, CHỈ nhánh thật (KHÔNG gọi FCM/audit trực tiếp — AuditSubscriber tự ghi). Validate: `amount` int ≥ 1 và ≤ subtotal hiện hành (tính qua `computeOrderTotals` — vượt → 400 fieldErrors `amount`); đơn 0 dòng → 400. Thiếu quyền (`quotes.create_edit` một mình KHÔNG đủ) → 403; đơn ma → 404; status khác `baogia` → 409. Trong `choduyet`, `assertMutable` chặn MỌI mutation dòng/meta/scope (nội dung đơn đóng băng suốt kỳ duyệt).
2. **Endpoint Duyệt/Từ chối (FR-18, AD-18):** **Given** Đơn `choduyet` có approval `cho_duyet`, **When** `POST /orders/:id/duyet-chiet-khau` body `{approve, reason?}` bởi người có `discounts.approve`, **Then** interactive tx: (a) cổng atomic trên CHÍNH row approval: `updateMany({where: {id: approvalId, status: 'cho_duyet'}, data: {status: approve ? 'dong_y' : 'tu_choi', resolvedByAccountId, resolveNote, resolvedAt}})` + `count === 1`; (b) NẾU từ chối: `tx.order.updateMany({where: {id, status: 'choduyet'}, data: {status: 'baogia'}})` count phải = 1 (đơn quay về Báo giá, sửa lại được); NẾU đồng ý: KHÔNG đổi status đơn (vẫn `choduyet` — "được Chốt", xem AC #3). `reason` BẮT BUỘC khi `approve=false` (thiếu → 400 fieldErrors `reason`), optional khi đồng ý. Publish `DiscountResolved` (mang `approved` + `reason` cho Epic 9) SAU commit. Retry cùng decision trên approval đã resolve → 200 idempotent trả view hiện tại, KHÔNG event; decision NGƯỢC → 409. Không approval `cho_duyet` nào → 409. Thiếu quyền (`discounts.apply` một mình KHÔNG duyệt được — nghịch đảo proof) → 403.
3. **Chốt sau duyệt + snapshot chiết khấu (FR-5, AD-16, spine ChoDuyet→DaChot "duyệt then Chốt"):** **Given** Đơn `choduyet` có approval `dong_y`, **When** `POST /orders/:id/chot` HIỆN CÓ bởi người có `orders.confirm`, **Then** `confirm()` mở rộng: cho chốt từ `choduyet` KHI approval mới nhất là `dong_y` (chưa duyệt/`tu_choi` → 409 "Chiết khấu chưa được duyệt"); cổng atomic dùng status quan sát được (`{id, status: 'choduyet'} → 'dachot'`); snapshot thêm `OrderVersion.discountAmount` = amount đã duyệt (đường `baogia` → `dachot` giữ NGUYÊN hành vi cũ, `discountAmount` = null). Tiền: `computeOrderTotals` (MỘT hàm duy nhất) mở rộng input `discountAmount` (default 0) — `vatBase = subtotal − discountAmount`, `VAT = round-half-up(vatBase × vatRate / 100)` vẫn MỘT điểm làm tròn duy nhất; `POST /orders/preview-total` nhận optional `discountAmount` (int ≥ 0, > subtotal → 400) và echo lại trong response. Sau chốt, giá + chiết khấu đóng băng trên version (sửa catalog không hồi tố). Mở lại (`mo-lai`) sau đó → version MỚI KHÔNG mang chiết khấu (muốn giảm tiếp phải áp + duyệt lại); `revise()` từ `choduyet` vẫn 409 (test hiện có giữ nguyên).
4. **Danh sách chờ duyệt + biên ước tính (FR-18, FR-37, AD-4):** **Given** người có `discounts.approve`, **When** `GET /orders/cho-duyet-chiet-khau` (route static ĐẶT TRƯỚC `:id`), **Then** trả mảng item: `{orderId, customerSdt, amount, requestNote, requestedByAccountId, requestedByDisplayName, requestedAt, subtotal, afterDiscount, lines: [{name, qty, unitPrice, estimatedMarginPct}]}` — `subtotal`/`afterDiscount` tính backend qua `computeOrderTotals({applyVat: false, discountAmount})`; `estimatedMarginPct` = `round-half-up((unitPrice − Product.costPrice) × 100 / unitPrice)` integer percent, đọc `Product.costPrice` HIỆN HÀNH (biên ước tính — chưa xuất kho chưa biết giá vốn thật), null khi dòng không có `productId` hoặc `unitPrice = 0`. **Fence `costs.view` (FR-37 verbatim):** `estimatedMarginPct` CHỈ xuất hiện khi actor có THÊM `costs.view` (margin lộ ngược ra costPrice); thiếu → field null trên mọi dòng, response không chứa costPrice dưới bất kỳ dạng nào — e2e chứng minh cả hai phía. Thiếu `discounts.approve` → 403.
5. **UI màn Tạo báo giá 2 nền tảng (UX-DR-20, UX-DR-22, parity):** **Given** đơn `baogia` editable, người có `discounts.apply`, **Then** nút "Áp chiết khấu" (hàng nút dưới khối Tổng kết, cạnh nút Chốt, bọc Gate `discountsApply`) mở MỘT dialog (không chồng 2 tầng overlay) gồm Field "Mức chiết khấu (đ)" + Field "Lý do đề xuất" (optional) + câu hệ quả byte-identical (Dev Notes) + nút Gửi duyệt/Huỷ → port `applyDiscount(orderId, {amount, note?})` → `setOrder(kết quả)`; lỗi → Banner + state NGUYÊN (pattern k). **Given** đơn `choduyet` (so bằng HẰNG `ORDER_STATUS_CHODUYET`/`kOrderStatusChoduyet` import từ port — guard n mở rộng cấm literal `'choduyet'` trong màn), **Then** màn read-only + Banner trạng thái theo `order.discount.status`: `cho_duyet` → Banner warn chờ duyệt; `dong_y` → Banner info "đã duyệt — có thể chốt" + nút Chốt HIỆN LẠI (Gate `ordersConfirm`, chốt từ choduyet); về `baogia` sau `tu_choi` → Banner warn kèm `resolveNote`. Khối Tổng kết thêm dòng "Chiết khấu" (chỉ hiện khi có, số từ backend — client CẤM số học tiền); `refreshTotals` echo `discountAmount` khi order mang chiết khấu hiệu lực. `OrderResponseDto` + `Order` type 2 port thêm `discount` (nullable: `{amount, status, requestNote, resolveNote, requestedAt, resolvedAt}` — approval MỚI NHẤT). Widget test mobile BẮT BUỘC (C-4) gồm error case.
6. **Màn Duyệt chiết khấu MỚI 2 nền tảng (`s-discount-approval`, UX-DR-20, UX-DR-22):** **Given** người có `discounts.approve`, **Then** màn mới `DiscountApprovalScreen` (web) / `discount_approval_screen.dart` (mobile): danh sách chờ duyệt (Đơn·Khách / Mức giảm / Người đề xuất / chip `StatusChip choduyet` — label mặc định "Chờ duyệt") từ `listPendingDiscounts()`; chọn item → panel/màn chi tiết: Giá gốc, Chiết khấu, Sau chiết khấu (số backend), bảng dòng kèm cột "Biên ước tính" (render `X%` từ `estimatedMarginPct`, "—" khi null, kèm chú thích nhãn ước tính byte-identical), Lý do đề xuất, Field "Lý do duyệt / từ chối (bắt buộc khi từ chối)" + nút "Từ chối" (danger — thiếu lý do thì chặn tại chỗ, không gọi port) / "Đồng ý chiết khấu" (primary); mỗi nút → ConfirmDialog/AppConfirmDialog hệ quả byte-identical → port `resolveDiscount(orderId, {approve, reason?})` → refresh danh sách; lỗi → Banner + state nguyên; danh sách rỗng → EmptyState; loading → Skeleton; lỗi tải → ErrorState + Thử lại. List/empty/error/loading theo UX-DR-19. KHÔNG hạn mức tự quyết — KHÔNG cổng phụ nào cho tự duyệt (copy mockup "vượt hạn mức/chỉ Giám đốc" là STALE — bỏ). Widget test mobile BẮT BUỘC. KHÔNG áp dụng copy đổi trạng thái bằng chip (UX-DR-23).
7. **Guards + parity + hồ sơ sinh:** `orders.test.mjs` cập nhật (c.2 += `applyDiscount`; e += nhãn mới; n += cấm `'choduyet'`; h.3 formula fake đổi base `vatBase` — mutation-check lại); guard file MỚI `design-system/screens/discount-approval.test.mjs` (khuôn orders.test.mjs: compose-only, port-only, permission-literal ban, money-arithmetic ban — biên/afterDiscount là SỐ PORT TRẢ, cấm client tính, label byte-identical, catch-reset ban, shell hosting); `parity.test.mjs` block 4.7 (3 cặp method + `ApplyDiscountInput`/`ResolveDiscountInput`/`DiscountPendingItem` twin + 2 hằng `ORDER_STATUS_CHODUYET`/`kOrderStatusChoduyet` sống ở PORT file); `permissions.json` + registry KHÔNG đổi (2 key `discounts.apply`/`discounts.approve` CÓ SẴN); OpenAPI regen.
